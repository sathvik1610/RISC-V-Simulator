How the machine works

Hartbeat models a small chip: several harts (RISC-V's own word for a hardware thread — a core), each walking instructions through a five-stage pipeline, all sharing one cache hierarchy and one memory. Everything below is the actual mechanism this simulator runs — not a simplified retelling.

Input → output, step by step

  1. You write assembly.An optional .data block declares named word arrays; a .text block holds labeled instructions from the supported subset (arithmetic, load/store, branch, jump, sync, halt).
  2. Assemble resolves it once.Labels become instruction indices, .data names become byte addresses, and every core is given its own copy of the register file, program counter, and private L1I/L1D — all pointed at the same instruction list and the same backing memory.
  3. Every cycle, fetch runs first.The centralized fetch unit checks each core in turn: if its front slot is empty and it isn't halted, it pulls the next instruction and advances that core's PC.
  4. Stages resolve back-to-front.Writeback, then Memory, then Execute, then Decode all update before Fetch does — so a value can only ever move one stage per cycle, exactly like flip-flops latching on one clock edge.
  5. Hazards are caught in Decode/Execute.A register still in flight is forwarded straight from the Execute or Memory stage if forwarding is on; otherwise Decode stalls until it's safely written back. A taken branch or jump flushes anything fetched past it and redirects the PC.
  6. Loads and stores walk the hierarchy.Every memory op checks private L1D, then shared L2, then main memory, paying each level's latency only on a miss — or bypasses all of it via the scratchpad.
  7. Sync is the checkpoint.A core hitting sync stalls until every other active core arrives too; on release, every core's L1D is written back and invalidated — a coherent view of memory, enforced only at that instant.
  8. You read the result.Final registers and memory, retired-instruction counts, stalls, flushes, and per-cache hit rates come back as the simulator's output — plus a full cycle-by-cycle trace for any instruction you want to inspect.

What this web version simplifies

This tab runs a from-scratch JavaScript engine built to demonstrate the same mechanisms as the C++ reference simulator in Final_Simulator/, entirely in your browser — no server, no build step. One thing is intentionally simplified for clarity: every stage holds exactly one in-flight instruction rather than a multi-deep queue, and fetch bandwidth isn't separately capped beyond each core's own single fetch slot. Everything else — pipeline ordering, forwarding, stalling, predict-not-taken branch flushing, the LRU/FIFO replacement choice, the cache hierarchy, the scratchpad, and the sync-barrier coherence model — follows the same logic as the original, and every one of those is exposed as a control or a readout in the Simulator tab rather than left to run invisibly.
